# 05 · 混元 3D 接口接入与队列调度

> 目标：用一行 cURL 生成一个 3D 模型，再把它变成能批量跑、扛得住限流和余额不足的生产管线。
> 预计 35 分钟 · 前置：第 01 篇（会用 Python 更佳）

---

## 先说接口，一句话版本

混元生3D 有一个 **OpenAI 兼容端点**，只要 API Key，**不需要 SecretId / SecretKey 签名**：

```bash
curl -X POST 'https://api.ai3d.cloud.tencent.com/v1/ai3d/submit' \
  -H 'Authorization: sk-你的KEY' \
  -H 'Content-Type: application/json' \
  -d '{"Prompt":"一只小猫"}'
```

返回：

```json
{"Response": {"RequestId": "...", "JobId": "1514534634355982336"}}
```

查任务：

```bash
curl -X POST 'https://api.ai3d.cloud.tencent.com/v1/ai3d/query' \
  -H 'Authorization: sk-你的KEY' \
  -H 'Content-Type: application/json' \
  -d '{"JobId":"1514534634355982336"}'
```

## 步骤 1：搞清参数，别猜

提交任务的完整参数（图生 3D 才是我们要的）：

| 参数 | 说明 | 我们的取值 |
|---|---|---|
| `Model` | `3.0` / `3.1`（3.1 支持更多视角，但不支持 LowPoly） | 主角 3.1，鱼 3.0 |
| `ImageBase64` | 输入图，单边 128–5000px，base64 后 ≤6MB | 参考图转 base64 |
| `MultiViewImages` | 多视角数组，元素是 `{ViewType, ViewImageBase64}` | 主角传 `left` + `back` |
| `FaceCount` | 面数 3000–1500000 | 主角 15000，鱼 6000–8000 |
| `EnablePBR` | 是否生成 PBR 材质 | 主角 true，鱼 false |
| `GenerateType` | `Normal` / `LowPoly` / `Geometry` / `Sketch` | Normal |

**注意：`Prompt` 和 `ImageBase64` 不能同时传**，二选一。

### 我们为什么选图生 3D

文生 3D 出来的东西不可控。而我们手上已经有 ComfyUI 生成的低多边形参考图（白底、侧视、风格统一），
喂进去做图生 3D，风格一致性高得多：

```
ref3d/char_front.png  + char_side.png + char_back.png  → 主角
ref3d/fish_bluefin.png                                  → 蓝鳍金枪
```

## 步骤 2：第一个坑——"并发 3"不是"3 个同时跑"

文档写的是"默认提供 3 个并发"，我理解成"最多 3 个任务并行处理"，于是循环提交了 12 次。

实际返回：

```json
{"Error": {"Code": "RequestLimitExceeded.JobNumExceed",
           "Message": "当前已达到3个任务上限，请稍后重试"}}
```

**它是"未完成任务数 ≤ 3"，不是"并行线程数 ≤ 3"。**
任务排队等待也算占坑，所以必须**完成一个再补一个**。

## 步骤 3：写一个队列调度器

`tools/asset_pipeline/hy3d_gen.py` 的核心就三件事：提交、轮询、下载。

```python
MAX_INFLIGHT = 3

def run_queue(spec_path, timeout=3600):
    specs = json.load(open(spec_path, encoding="utf-8"))
    specs = {k: v for k, v in specs.items() if not k.startswith("_")}  # 允许写注释字段
    queue = [...]           # 还没提交的
    while queue and time.time() < deadline:
        inflight = [n for n, v in st.items() if v.get("status") == "RUN"]

        # 1. 先收割已完成的（任务可能在我们离开时完成了）
        for n in list(queue):
            if st[n].get("status") == "DONE":
                download_all([n]); queue.remove(n)

        # 2. 有空位就补
        if queue and len(inflight) < MAX_INFLIGHT:
            for n in list(queue):
                if len(inflight) >= MAX_INFLIGHT: break
                r = submit_one(n, specs[n])
                if r.get("status") == "RUN":
                    inflight.append(n)
                elif "JobNumExceed" in err:
                    break        # 名额满了，本轮不再尝试
                else:
                    queue.remove(n)

        # 3. 轮询在飞任务
        for n in inflight:
            resp = query(st[n]["job_id"])["Response"]
            if resp["Status"] == "DONE":
                st[n].update(status="DONE", files=resp["ResultFile3Ds"])
                download_all([n])
            elif resp["Status"] in ("FAIL", "FAILED"):
                st[n].update(status="FAIL", error=resp)
        time.sleep(10)
```

三个设计决定值得说：

1. **状态落盘**（`hy3d_out/jobs.json`）。进程随时可能被杀，重启后要能从断点继续，不能重复扣积分。
2. **提交/轮询/下载解耦**。沙箱里长驻轮询进程会被回收，所以设计成"按 prompt_id 精确收割"。
3. **`_` 开头的 key 当注释**。JSON 不支持注释，用这个约定写说明，加载时过滤掉。

## 步骤 4：第二个坑——两个进程同时写状态文件

我犯的错：一个后台进程在轮询主角任务，另一个进程在跑鱼的队列。**两边都在读写同一个 `jobs.json`**，
结果后写的覆盖先写的，几个已提交任务的 JobId 被抹掉 → 变成了"孤儿任务"（照扣积分，但再也收不回来）。

修法很简单：**同一时刻只允许一个进程写状态文件**。

```python
def save_state(st):
    tmp = STATE + ".tmp"
    open(tmp, "w").write(json.dumps(st, ensure_ascii=False, indent=2))
    os.replace(tmp, STATE)     # 原子替换，避免写一半被读到
```

原子替换只能防"读到半个文件"，防不了"覆盖别人"。**写状态的东西必须是单例进程。**

## 步骤 5：积分是会用完的

每个任务的消耗记录在返回里：

```json
{
  "ResultCreditConsumed": 30,
  "ResultCreditDetails": "{\"FaceCount\":10,\"GenerateType-Normal\":20}"
}
```

| 任务 | 明细 | 合计 |
|---|---|---|
| 鱼（6000 面 + Normal） | FaceCount 10 + Normal 20 | **30** |
| 主角（+ 多视角 + PBR） | 30 + MultiViewImages 10 + Pbr 10 | **50** |

跑完 1 个主角 + 5 条鱼 = **200 积分**，第 6 条鱼开始返回：

```json
{"Error": {"Code": "ResourceInsufficient"}}
```

所以队列脚本必须能区分两种失败：

- `JobNumExceed` → **等**（名额问题，稍后会好）
- `ResourceInsufficient` → **停**（余额问题，等多久都没用）

```python
if "JobNumExceed" in err:
    break
elif "ResourceInsufficient" in err:
    print("积分不足，队列中止")
    return
```

不清这两种错误，脚本会空转一整晚，第二天你发现一条鱼都没多。

## 步骤 6：跑起来

```bash
cd tools/asset_pipeline
python hy3d_client.py probe                 # 先探通：用一个假 JobId 查，不消耗额度
python hy3d_gen.py run spec_all.json        # 全量队列
python hy3d_gen.py run spec_remaining.json  # 充值后补剩下的
```

`probe` 那步特别值得写：用假 JobId 查一次，能确认三件事——网络通、Key 有效、错误格式符合预期。
**不要拿真实任务去试网络。**

## 步骤 7：参考图决定成品上限

第一版我用 ComfyUI 生成参考图时没管背景，结果 3D 模型带着"底座"出来了。
后面统一成：**白底或纯色底、单对象、侧视或正视、风格统一**。

`tools/asset_pipeline/ref3d/` 下就是最终用的参考图。生成它们的方法见仓库外部的 ComfyUI 工作流笔记，
但规则很简单：

- 鱼：侧视、头朝左、白底、低多边形平涂
- 人：正视 + 左视 + 背视三张，姿势一致，白底
